> Last update: 2026-08-09

Audit du code (~3 700 lignes) + de l'état réel de la base Firestore, demandé par Serge.
Axes : robustesse, fiabilité, pérennité de la data, doublons, simplicité.

## TIER 0 — Critique, la data est en danger maintenant

### 0.1 — Les règles Firestore déployées sont un open bar

Les règles **réellement déployées** (récupérées via l'API `firebaserules.googleapis.com`,
release `cloud.firestore` du **2026-02-24**, jamais mise à jour depuis) :

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.auth != null;
    }
  }
}
```

**N'importe quel compte Google authentifié peut lire ET écrire n'importe quoi** : effacer les
38 semaines, réécrire la liste du staff, vider les logs. Or :
- l'app est publique sur GitHub Pages,
- `firebase-applet-config.json` (projectId, apiKey) est dans un repo **public**,
- le bouton « Sign in with Google » accepte **tout le monde**, pas seulement les employés.

Le fichier `firestore.rules` du repo — bien meilleur — **n'a jamais été déployé**. Le changelog
du 2026-04-04 le disait déjà (« Deploy : pas encore fait ») ; c'est maintenant vérifié
empiriquement, pas supposé.

**⚠️ Piège : déployer `firestore.rules` en l'état casserait deux choses.** Vérifié sur la data réelle :

1. **La création de logs serait rejetée.** `isValidLog()` exige `data.id is string`, or
   `saveLogToFirebase()` fait un `addDoc()` sans champ `id` (Firestore génère l'id du document,
   il n'est pas dans les données). Les 3 671 logs existants ont bien les champs
   `userId, userName, action, details, timestamp` — **et pas de `id`**. Il faut corriger la règle
   (retirer `data.id`) ou le code, avant de déployer.
2. **Les non-admins verraient une erreur non gérée.** `match /logs/{logId}` a
   `allow read: if isAdmin()`, mais `subscribeToLogs()` est appelée pour tous les utilisateurs.
   Un employé non-admin déclencherait un `permission-denied` qui remonte dans
   `handleFirestoreError` → `throw` dans un callback `onSnapshot` → rejet non capturé.

En revanche la validation des semaines passerait sans problème sur la data existante — vérifié :
max 30 shifts sur une semaine (plafond de la règle : 100), `dayIndex` toujours entier entre 0 et 6,
`endTime > startTime` partout, `id`/`staffId`/`updatedAt` toujours présents. **0 anomalie sur 964 shifts.**

### 0.2 — Aucune sauvegarde

Firestore en plan Spark (gratuit) : **pas de PITR, pas d'export automatique, pas de corbeille**.
Un `setDoc` malheureux, un « Delete Week » de trop, un script mal ciblé = perte définitive.

Ce n'est pas théorique : l'incident du **2026-05-04** (liste du staff écrasée par `INITIAL_STAFF`)
n'a été réparable que parce qu'un dump JSON traînait **par hasard** en local
(`tmp-april-raw.json`). Sans ce fichier, les 11 employés, leurs emails et leurs couleurs étaient
perdus. Le filet de sécurité était un accident, pas un dispositif.

## TIER 1 — Robustesse des écritures

### 1.1 — Écrasement silencieux entre admins (`services/firebaseService.ts:152`)
`saveShiftsToFirebase()` fait un `setDoc()` **sans `merge`, sans transaction**, sur le tableau
`shifts` entier. Il y a 3 admins (Serge, Tatiana, Sinar). Si deux d'entre eux éditent la même
semaine en même temps, le second écrase intégralement le travail du premier — sans conflit,
sans avertissement, sans trace autre qu'une ligne de log.

Correctif : `runTransaction()` + un compteur de version (ou comparaison de `updatedAt`), et un
message « cette semaine a été modifiée entre-temps, recharge » plutôt qu'un écrasement muet.

### 1.2 — `shifts` non défendu à la lecture (`firebaseService.ts:231`)
`callback(snap.data().shifts as Shift[])` — le `as` est un mensonge au compilateur : si le champ
`shifts` manque ou n'est pas un tableau, `undefined` part dans le state React et casse les `.map()`
en aval. Un `Array.isArray()` suffit.

### 1.3 — `handleFirestoreError` relance dans des callbacks (`firebaseService.ts:64`)
La fonction `throw` une `Error` contenant un JSON avec **l'email et l'uid de l'utilisateur**.
Appelée depuis les callbacks d'erreur de `onSnapshot`, ce `throw` ne peut être attrapé par personne
→ rejet non géré. Et l'app n'affiche jamais rien à l'utilisateur : une écriture qui échoue est
invisible (le badge passe quand même en « Saved »).

### 1.4 — Le mode bootstrap ouvre l'écriture à tous (`App.tsx:148`)
`isBootstrapMode` est vrai dès qu'aucun membre n'a à la fois `role: 'admin'` et un email non vide.
Dans ce cas `isReadOnly` devient `false` **pour n'importe quel utilisateur connecté**. C'est
exactement l'état qui suit une corruption de la staff list — soit le pire moment pour ouvrir les
droits. Le garde-fou serveur devrait rattraper, sauf qu'aujourd'hui les règles déployées ne
bloquent rien (voir 0.1).

### 1.5 — « Copy Previous Week » écrase sans confirmation (`Sidebar.tsx:324`)
Le bouton appelle `onCopyLastWeek` **directement, sans `confirm()`** — contrairement à
« Delete Week » qui en a un. Or `handleCopyLastWeek()` fait un `handleUpdateShifts()` qui
**remplace intégralement** les shifts de la semaine courante. Un clic de trop sur une semaine
déjà planifiée, et tout le planning est remplacé par celui de la semaine précédente. Undo
rattrape si on s'en aperçoit tout de suite — sinon c'est perdu au prochain rechargement.
(Cas sans risque : si la semaine précédente est vide, `if (prevShifts?.length)` bloque.)

### 1.6 — Le badge « Saved » ment
`triggerSyncFeedback()` est appelé juste après le `await`, sans vérifier que l'écriture a réussi
(les erreurs sont avalées plus haut). L'utilisateur voit « Saved » même quand rien n'a été écrit.

## PLAN DE TRAVAIL (v2 — intègre le contre-audit)

Principe d'ordonnancement : **d'abord un filet, ensuite les fuites qui coûtent le moins cher à
boucher, ensuite les portes ouvertes, ensuite le solide, enfin le cosmétique.** Chaque phase est
livrable et testable seule. À valider par Serge phase par phase.

### Phase 0 — Le filet (à faire avant tout le reste) — réf. 0.2
Rien d'autre ne se touche tant que ceci n'est pas en place.

1. **Backup complet immédiat**, one-shot, avant toute modification
2. **Script de backup automatisé** : dump `weeks` + `settings` + `logs` en JSON horodaté
   - Destination `G:\My Drive\...\Backups\shiftmaster\` — le Drive est synchronisé en local,
     donc copie locale **et** cloud sans effort supplémentaire
   - Rotation : quotidien gardé 30 jours + un mensuel gardé indéfiniment
   - Tâche planifiée Windows
   - Même esprit que les 7 versions du Prep Manager, mais automatisé
3. **Vérifier la restauration** : rejouer un backup vers un projet de test. Un backup jamais
   restauré n'est pas un backup.

### Phase 1 — Quick wins anti-corruption (2 fixes courts, gros retour) — réf. A.1, 1.5
Deux bugs qui peuvent frapper pendant un usage parfaitement normal, pour quelques lignes de code.

1. **Vider `past`/`future` au changement de semaine** (A.1). Sans ça, Undo après navigation
   écrase le planning d'une semaine par celui d'une autre. ~2 lignes.
2. **Confirmation sur « Copy Previous Week »** (1.5), alignée sur celle de « Delete Week ».

### Phase 2 — Fermer l'open bar Firestore — réf. 0.1, A.2
Dans cet ordre précis, car les points 1 et 2 sont des **prérequis** au déploiement :

1. **Corriger `isValidLog`** : retirer l'exigence `data.id` (sinon plus aucun log ne passe)
2. **Corriger le `read` sur `/logs`** : le passer à `isStaffOrGuest` (sinon les non-admins
   plantent) — ou ne plus souscrire aux logs quand on n'est pas admin
3. **Dénormaliser `staffEmails: []`** dans `settings/staff`, écrit par `saveStaffToFirebase`
   exactement comme `admins` l'est déjà — sans ça, `isStaffOrGuest` ne peut rien vérifier (A.2)
4. **Réécrire `isStaffOrGuest`** sur ce champ et **la brancher** sur `/weeks` et `/settings`
5. **Borner `startTime`/`endTime`** à 8..24 dans `isValidShift`
6. **Tester à l'émulateur**, déployer, puis **vérifier la release via l'API** (comme dans cet
   audit) — ne pas se fier au fait que la commande n'a pas renvoyé d'erreur

### Phase 3 — Écritures sûres — réf. 1.1, 1.2, 1.3, 1.4, 1.6, A.4
1. `runTransaction` + version sur `weeks/{weekId}` : fin des écrasements silencieux entre les
   3 admins ; en cas de conflit, message « modifiée entre-temps, recharge »
2. Remonter les erreurs d'écriture à l'écran ; le badge ne passe à « Saved » qu'en cas de
   succès réel (1.6)
3. `Array.isArray()` sur `shifts` à la lecture (1.2)
4. `handleFirestoreError` : ne plus `throw` depuis un callback `onSnapshot`, ne plus sérialiser
   l'email de l'utilisateur dans le message (1.3)
5. Fermer la fenêtre bootstrap : distinguer « staff pas encore chargé » de « staff vide », et
   ne jamais accorder l'écriture pendant le chargement (1.4 + A.4)
6. Optionnel : garder les N dernières versions d'une semaine dans une sous-collection, pour
   revenir en arrière sans passer par un backup complet

### Phase 4 — Cycle de vie employé (finir le WIP en cours) — réf. A.3
1. **Soft-delete** : « retirer » un employé pose une `endDate` au lieu de le sortir de la liste.
   Son historique reste visible, les heures passées restent exploitables pour la paie
2. Saisir les `startDate` des 9 employés (aujourd'hui : **0 sur 9** renseignés, donc tout le
   filtrage écrit est inerte)
3. Si un vrai retrait définitif reste nécessaire, sa confirmation doit annoncer la conséquence
   (« son historique n'apparaîtra plus dans les plannings »)

### Phase 5 — Nettoyage — réf. Tier 2
Dans l'ordre : suppression du code mort (2.1 → 2.5), branchement de `settings/global` pour le
fuseau **ou** suppression des deux fonctions inutilisées (2.2 — choisir, ne pas laisser en l'état),
découpage d'`App.tsx`, purge/archivage des logs (2.11).

### Ce qui a changé depuis la v1 du plan
- Phase 1 est **nouvelle** : les deux bugs anti-corruption passent devant les règles, parce
  qu'ils coûtent quelques lignes et frappent en usage normal
- Phase 2 gagne les étapes 3 et 4 : brancher `isStaffOrGuest` telle quelle n'aurait **rien
  restreint** (A.2), il faut d'abord dénormaliser `staffEmails`
- Phase 4 est **nouvelle** : le WIP `startDate`/`endDate` n'était pas vu comme un sujet de
  robustesse, alors qu'il est la bonne réponse au hard-delete (A.3)

## Addendum — contre-audit (Fable, même jour)

Passe indépendante de vérification. Les Tier 0/1/2 ci-dessus sont confirmés. Quatre ajouts :

### A.1 — 🔴 Undo/redo traverse les semaines (corruption de data)
`past`/`future` (App.tsx:110) ne sont **pas vidés au changement de semaine** (l'effet sur
`weekId` ne les reset pas). `undo()` applique `past[0]` via `handleUpdateShifts`, qui écrit sur
le **weekId courant**. Éditer la semaine A, naviguer vers B, cliquer Undo → le planning de A
écrase celui de B en base. Vérifié en lecture de code, pas testé en runtime.
**Fix** : `setPast([]); setFuture([])` dans l'effet de changement de `weekId`.

### A.2 — 🟠 `isStaffOrGuest` est inefficace telle qu'écrite
Sa clause `get(...).data.list.size() > 0` est vraie dès que la staff list est non vide, donc
toujours → la fonction équivaut à `isAuthenticated()`. La brancher (étape 2 du plan) ne
restreindrait rien. Il faut dénormaliser un champ `staffEmails: []` dans `settings/staff`
(comme `admins`), écrit par `saveStaffToFirebase`, et tester `request.auth.token.email in`
ce champ.

### A.3 — 🟠 Hard-delete d'un employé = historique invisible (enjeu paie)
`onRemove` retire l'employé de la liste ; ses shifts restent en base mais Calendar/EmployeeView
font `if (!staffMember) return null` → tout son historique disparaît de l'affichage.
Or c'est la source des heures pour le comptable. **Fix** : remplacer le hard-delete par un
soft-delete (poser `endDate` — le WIP en cours est la bonne réponse).

**Deux nuances vérifiées** (contre-vérification de l'addendum) :
1. Une confirmation **existe** (`StaffModal.tsx:176`, « Remove X from the roster? »). Le
   problème n'est pas son absence, mais qu'elle ne dit pas que tout l'historique de la personne
   va devenir invisible. La disparition est silencieuse, pas la suppression.
2. **La data n'est pas perdue** : les shifts restent en base avec leur `staffId`, et
   `scripts/read-firebase.js` (qui lit les documents `weeks` bruts) les voit toujours. C'est un
   problème d'affichage, pas de destruction — donc grave mais réversible.

### A.4 — 🟡 Fenêtre d'écriture au démarrage
`staffList` démarre à `[]` → `isBootstrapMode` vrai → `isReadOnly` faux pour tout utilisateur
connecté pendant les premières secondes, jusqu'au premier snapshot staff. Aggrave le 1.4.

Mineurs : `isValidShift` ne borne pas les heures à 8..24 ; tout compte authentifié peut spammer
`/logs` en création même avec les règles du repo ; `displayName` envoyé à ui-avatars.com
(cosmétique, hors capture PNG) ; IDs `Math.random` acceptables ici.

**Impact sur le plan** : inchangé (backup → règles → écritures sûres → nettoyage), avec
A.1 en tête de l'étape 3, et l'étape 2 passe par la dénormalisation `staffEmails` (A.2).
